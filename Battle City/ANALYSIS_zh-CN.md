# Battle City 游戏机制分析笔记（中文）

本文档记录从本目录反汇编源码中读出的**游戏机制结论**，供复刻/移植时查阅，避免重复通读 8772 行汇编。

- 分析对象：`bank_FF.asm`（主反汇编，$C000-$FFFF）、`bank_ram.inc`（RAM 映射）、`CHR_ROM.chr`（图形）
- 对照材料：`_misc/Russian disassembly by Griever.asm`、[Habr 逆向文章](https://habr.com/ru/articles/142126/)
- 每条结论都标注了**标签名 + $地址**，可回源码逐条核对
- 版本：Battle City (J)。市面上的 Tank 1990 等盗版改版可能改过逻辑，不适用本文

## 1. 坐标系与地形数据结构

三级粒度，理解这三层是理解一切地形交互的前提：

| 层级 | 尺寸 | 用途 |
|---|---|---|
| block（关卡数据单位） | 16×16 px | 关卡文件里每格 4 bit |
| **tile（运行期地形单位）** | **8×8 px** | 内存中每个 tile 一字节；**坦克通行判定的最小单位** |
| **子块（破坏单位）** | **4×4 px** | 砖 tile 低 4 位的存在掩码 |

- 战场 = 13×13 个 block = 208×208 px
- 每个 block = 2×2 个 tile；运行期地形按 tile 存为一字节 tile ID
- 砖 tile 的**低 4 位是四个 4×4 子块的存在掩码**：`$0F` = 满砖，`$00` = 空
- 子块掩码位序（`sub_D725` @ `$D725`）：`bit=1; if(pos_Y&4) bit<<=2; if(pos_X&4) bit<<=1`
  → **bit0 = 左上，bit1 = 右上，bit2 = 左下，bit3 = 右下**

### tile ID 取值

| 值 | 含义 |
|---|---|
| `$00` | 空 |
| `$01`-`$0F` | 砖（低 4 位为子块掩码） |
| `$10` | 钢墙 |
| `$11` | 战场灰色外框（连 3 星弹都打不掉） |
| `$12` | 水 |
| `$21` | 冰 |
| `$22` | 树（草丛） |
| `$C8`-`$CB` | 老鹰（基地） |
| `>= $80` | 坦克占位的「隐形墙」 |

### 关卡数据格式

- `incbin/stages/stage_01..35.bin`，**每关 91 字节**（13×14 个 block、每 block 4 bit）
- block 类型表 `tbl_DACB` @ `$DACB` 共 16 种，每种展开成 4 个 tile：

  | 值 | 含义 | 展开 |
  |---|---|---|
  | `00` | 右半砖 | `[00,0F,00,0F]` |
  | `01` | 下半砖 | |
  | `02` | 左半砖 | |
  | `03` | 上半砖 | |
  | `04` | 整砖 | `[0F,0F,0F,0F]` |
  | `05`-`08` | 四种半钢 | |
  | `09` | 整钢 | `[10,10,10,10]` |
  | `0A` | 水 | `[12,...]` |
  | `0B` | 树 | `[22,...]` |
  | `0C` | 冰 | `[21,...]` |
  | `0D` / `0F` | 空 | |

- **注意**：原版关卡数据里砖只有「整格 / 上下左右半格」，**没有 1/4 格**。
  基地外壳那圈砖是代码生成的，不在关卡文件里。

## 2. 炮弹与墙体交互

### 2.1 炮弹是一个点

- 出膛位置（`sub_E08C` @ `$E0A2-$E0B6`）：`bullet_pos = tank_pos + 8 * 方向单位向量`
- `tank_pos` 是**坦克中心**；坦克 16×16，实体范围 `[c-8, c+7]`

### 2.2 四个探测点（关键）

`sub_E604_bullets_movement` @ `$E642-$E688`：

设 `u` = **垂直于弹道方向**的坐标（竖直弹取 X，水平弹取 Y），沿弹道方向坐标恒等于子弹位置。
依次探测四点：

```
P1 = u        （总是检测）
P2 = u + 4    （仅当 P1 打掉了砖子块才检测）
P3 = u - 1    （总是检测）
P4 = u - 5    （仅当 P3 打掉了砖子块才检测）
```

- 方向分量取自 `tbl_EA49`(dX) = `[00,FF,00,01]`、`tbl_EA4D`(dY) = `[FF,00,01,00]`（0=上,1=左,2=下,3=右）
- 偏移量 = 4 × |垂直单位向量|，**所以偏移永远垂直于弹道**
- 覆盖像素区间 `[u-8, u+7]` = **16px，恰好等于坦克宽度**

### 2.3 单点命中判定

`sub_E69A` @ `$E69A`：

1. 取 `tile = field[y>>3][x>>3]`、`bit` = 4×4 掩码位
2. `(tile & (0xF0|bit)) == 0` → 此处为空，子弹继续飞
3. `(tile & 0xFC) == 0xC8` → 老鹰，游戏结束
4. `tile >= 0x12`（水/冰/树）→ **子弹穿过，不停**
5. 否则子弹在此爆炸（`status=$33`），并且：
   - `tile == 0x11`（外框）→ 什么都不掉
   - **3 星强弹**（`bullet_property & 0x02`）→ **整个 8×8 tile 直接写 0**（砖、钢通吃），返回 0（不触发外扩探测）
   - `tile == 0x10`（钢墙）普通弹 → 不掉
   - 砖（`$01`-`$0F`）→ `tile &= ~bit`，**只清掉命中的那 1 个 4×4 子块**（`sub_D743` @ `$D743`），返回 1（允许向外再探一格）

### 2.4 净效果

| 弹种 | 一发清除范围 | 打穿一整瓦（16px 厚）所需 |
|---|---|---|
| 普通弹 / 1-2 星 | **16 宽 × 4 深** | **4 发** |
| 3 星强弹 | **16 宽 × 8 深**，可破钢 | 2 发 |

- 慢弹 2px/帧但隔帧处理、快弹 4px/帧每帧处理 → 等价于**都是每前进 4px 检查一次**，故「一发只吃 4px 深」在两种弹速下都成立
- **子弹自身的通过判定只用 `u-1` 和 `u` 两点**，所以 8px 宽的通道子弹能过、16px 的坦克过不去（原版常见的「子弹能过、坦克过不去」窄缝）

### 2.5 残砖现象的成因

若内侧格（`u` 或 `u-1`）已经是空的，**外侧格根本不会被检测**，于是打不掉。
这就是坊间说的「砖墙打几发后剩下打不掉的残砖、仍然挡路」。

### 2.6 子弹属性

`sub_E08C` @ `$E0BC-$E0D5`，按 `tank_type & 0xF0` 设置 `bullet_property`：

| 坦克 | property | 含义 |
|---|---|---|
| 玩家 3 星（`$60`） | `$03` | 快弹 + **强弹**（整 tile 清零、可破钢） |
| 玩家 1-2 星（`$20`/`$40`） | `$01` | 仅快弹 |
| 200 分快弹敌军（`$C0`） | `$01` | 仅快弹 |
| 其余敌军 | `$00` | 普通 |

**1-2 星只是子弹变快，破坏范围与普通弹完全相同。**

## 3. 坦克

### 3.1 网格吸附（关键设计）

`$DBD5`「align player tank positions」：玩家**转向到垂直方向时**把坐标做 `pos = (pos+4) & 0xF8`，即**对齐到 8 像素网格**。

因此 `u` 恒为 8 的倍数，2.2 的四个探测点正好落在 4 个相邻的 4px 单元里，
**凿出的通道恰好等于开火坦克自身 16px 的投影——「开出的路必然够自己过」是刻意设计，不是巧合。**

> 敌方坦克没有显式的对齐指令，靠 AI「坐标 %8==0 时才换向」间接保证。

### 3.2 通行判定

`$DCD5-$DD02`：取坦克前方两角所在 tile，`tile == 0` 或 `tile >= 0x20`（空/冰/树）才可通行；
`tile >= 0x80`（坦克隐形墙/老鹰）或 `$01`-`$1F`（**任何残留砖 bit**、钢、水）都挡住。

> **一个 8×8 tile 必须 4 个子块全清空，坦克才能进入。**
> 俄文原文：«при уничтожении части кирпичного блока, танк не может въехать на освободившееся пространство — ведь сам тайл не был уничтожен»

## 4. CHR-ROM 图形资源索引

`CHR_ROM.chr` = 8192 字节 = **512 个 8×8 tile**。
格式：每 tile 16 字节，前 8 字节 bitplane0、后 8 字节 bitplane1，
像素值 = `bit(plane0) | bit(plane1)<<1`（4 个色值）。

### 字库位置（实测确认）

| 内容 | tile 索引 |
|---|---|
| 数字 `0`-`9` | **304-313** |
| 小写 `e` / `f` | 318 / 319 |
| `©` | 320 |
| 字母 `A`-`W` | **321-343**（连续） |
| 字母 `Y` | **345** |
| 右箭头 / 下划线等符号 | 347-351 附近 |
| `PAUSE` 大字 | 第 17 行（tile 272-287）区域 |
| `STAGE` 大字 | 第 18 行（tile 288-303）区域 |
| `namcot` 商标 | 第 22 行（tile 352-367）区域 |

> **`X` 和 `Z` 不存在**：这两个 tile 位置（344、346）被其他图形占用。
> 原因是原版全部文本（`HI-SCORE` / `STAGE` / `I-PLAYER` / `PTS` / `TOTAL` /
> `GAME OVER` / `PAUSE` / `NAMCOT` / `CONSTRUCTION`）都不含这两个字母，卡带空间被省下来了。
> **字库中也没有连字符**，`HI-SCORE` 的 `-` 需另找或自绘。

### 解码示例（Java）

```java
byte[] data = Files.readAllBytes(chrPath);
for (int row = 0; row < 8; row++) {
    int plane0 = data[tile * 16 + row] & 0xFF;
    int plane1 = data[tile * 16 + 8 + row] & 0xFF;
    for (int column = 0; column < 8; column++) {
        int bit = 7 - column;
        int value = ((plane0 >> bit) & 1) | (((plane1 >> bit) & 1) << 1);
        // value: 0=背景, 1..3=调色板索引
    }
}
```

## 5. 精灵表布局（pattern table 0）

已用 `CHR_ROM.chr` 逐像素校验：pattern table 0 的 256×256 区域按 16×16 坦克排成 8 行 8 列，
**四个象限是同一份索引图的四次调色板替换**（三次象限比对索引差 = 0）：

| 象限原点 | 调色板 |
|---|---|
| (0, 0) | palette 0 — 1P 黄 |
| (0, 128) | palette 1 — 2P 绿 |
| (128, 0) | palette 2 — 敌军银白 |
| (128, 128) | palette 3 — 红 |

**象限内行偏移（极易切错，务必核对）**：

| 行偏移 | 内容 |
|---|---|
| +0 / +16 / +32 / +48 | 玩家 0 / 1 / 2 / 3 星 |
| **+64 / +80 / +96 / +112** | **敌军 basic / fast / power / armor** |

**列偏移** = `方向 × 32 + 履带帧 × 16`，方向序 **U=0, L=1, D=2, R=3**。

### 精灵调色板

`sub_D53E_set_sprites_palette` @ `$D53E` 全程只写一次，不随关卡变。
`tbl_D555_sprites_palette` @ `$D555` = `0F,18,27,38 / 0F,0A,1B,3B / 0F,0C,10,20 / 0F,04,16,20`：

| # | 配色 | 三个前景色 |
|---|---|---|
| 0 | 1P 黄 | 暗橄榄 `#6B6B00` / 橙 `#E79C21` / 淡黄 `#E7E794` |
| 1 | 2P 绿 | 暗绿 `#005200` / 绿 `#008C31` / 淡绿 `#B5F7CE` |
| 2 | 敌军银白 | 暗青 `#00424A` / 灰 `#ADADAD` / 白 `#FFFFFF` |
| 3 | 红 | 暗紫 `#5A007B` / 红 `#B53121` / 白 `#FFFFFF` |

## 6. 敌军坦克的配色状态

`ram_tank_type`（`$00A8+X`）一个字节承载三件事：

- **bit7-5 种类**：`$00/$20/$40/$60` = 玩家 0-3 星，`$80/$A0/$C0/$E0` = 敌军 100/200/300/400 分
- **bit2**：道具携带者标志
- **bit1-0**：剩余装甲层数

### 装甲坦克（400 分）

**只换调色板，完全不换 tile**——绘制时 `tile = (type AND $F0) + wheels + dir*8`，低两位血量被掩掉，
所以四个血量状态的车型完全相同。

激活时 `ORA #$03` 得 `$E3`；每次中弹 `AND #$03` 非 0 则 `DEC`（`$E3→$E2→$E1→$E0`），为 0 才爆炸，共 4 发。

配色不是「每中一发换一个固定色」，而是**每帧在两色间交替**（NES 每帧换一次调色板、两帧一循环 = 30Hz，
CRT 上被眼睛积分成混合色）：`palette = tbl_E003[((frame<<2) + type) AND 7]`，
`tbl_E003` = `02,00,00,01,02,01,02,02`：

| 剩余装甲 | 交替配色 | 观感 |
|---|---|---|
| 4（满血） | 绿 ↔ 银白 | 青绿 `#004A25/#569C6F/#DAFBE6` |
| 3 | 黄 ↔ 银白 | 米黄 `#355625/#CAA467/#F3F3CA` |
| 2 | 黄 ↔ 绿 | 黄绿 `#355E00/#739429/#CEEFB1` |
| 1 | 恒定银白 | 与普通敌军无异 |

> **注意满血是绿色**，不是"受损才变色"。basic / fast / power 的低两位恒为 0 → `tbl[0]=tbl[4]=$02` → 全程银白，无任何变色。

### 道具携带者

走 `$DFBA` 独立分支且**优先级高于装甲配色**（原版先判 bit2）：
`palette = (frame>>3 AND 1) + 2`，即**银白 ↔ 红每 8 帧一换**（约 133 ms）。

装甲车恰好是携带者时（第 4/11/18 辆）类型被强制成 `$E4`：第一发命中先掉道具、
再因 `CMP #$E4` 多 `DEC` 一次 → `$E3`、然后常规 `DEC` → `$E2`，总血量仍 4 发，
但道具在第一发就掉、且永远不显示满血绿。

### 其他状态

- 冻结时钟：只拦移动，不改配色
- 玩家友军火 stun：整车隐现，每 8 帧切换
- 无敌头盔：独立叠加的精灵，**车身不变色**
- 出生星形：用 palette 3

## 7. 关卡结算画面

### 画面切换

全屏重绘，**不叠在战场上**：画进另一块 nametable（`$2800`），把 PPUCTRL 的 base nametable 切到 #2。
`sub_CEF7` 先关渲染 → 清缓冲 → 写属性表 → 整块拷贝 → 开渲染，
所以视觉上是**黑屏 1~2 帧后硬切**，没有淡入。

结束后 base nametable 复位，`sub_CC90_close_grey_curtain` @ `$CC90` 用灰 tile `$11`
**上下对开合拢 16 帧**（≈266 ms），再开幕进入下一关。

### 版式（32 列 × 30 行，每格 8×8；数字一律右对齐、抹前导零）

| 行 | 内容 |
|---|---|
| 3 | `HI-SCORE`（col 8-15）+ 最高分（右边界 col 23） |
| 5 | `STAGE`（col 12-16）+ 关号（右边界 col 19） |
| 7 | `Ⅰ-PLAYER`（col 3-10）、`Ⅱ-PLAYER`（col 21-28，仅双人） |
| 9 | 1P 总分（右边界 col 10）、2P 总分（右边界 col 28） |
| **12 / 15 / 18 / 21** | 四条统计行（100/200/300/400 分档），**间隔 3 行** |
| 22 | 横线：8 个 tile `$5C`（col 12-19）。**单人也照画整条**（原版小瑕疵） |
| 23 | `TOTAL`（col 6-10）+ 1P 总击杀（右边界 col 13）+ 2P（右边界 col 19） |
| 25 / 26 | `BONUS!` + `1000 PTS`（仅双人、非 game over、击杀多且还有命的一方） |

单条统计行的排列（左→右）：
`1P累计分 → PTS → 1P击杀数 → ←(tile $5B) → 坦克图标 → →(tile $5D) → 2P击杀数 → 2P累计分 → PTS`

> 坦克图标是**精灵**不是背景 tile（`sub_D0B8` 每帧重画），x=121..136，y=93/117/141/165。

### 动画时序（帧为单位，NTSC 1 帧 ≈ 16.64 ms）

**不是「逐行滑出」，而是「逐行计数」**：静态版式一次性全画出，真正的动画是四条统计行的
**数字从 0 开始逐个跳动累加**，一行数完再数下一行，从上往下。

| 阶段 | 帧数 |
|---|---|
| 最后一辆敌军被打掉 → 进结算 | 128 帧（≈2.13 s；有 GAME OVER 时 256 帧） |
| 画完版式后等待 | 30 帧（≈500 ms） |
| **每一次计数跳动** | **9 帧（≈150 ms）**，每跳播一记短「嘀」 |
| 档间停顿 | 20 帧（≈333 ms） |
| 四档数完 → 画 TOTAL | 30 帧 |
| TOTAL → BONUS 判定 | 15 帧 |
| 最后停留 | 120 帧（≈2.00 s） |

典型单人全清（8/5/4/3 分布）总时长 ≈ **475 帧 ≈ 7.9 s**；最短（0 杀）≈ 4.9 s。

音效：每次跳动同时触发 `ram_sfx_score_count_1`（`$0313`，方波）+ `_2`（`$0314`，噪声）。
**结算画面没有背景音乐**（进画面前已 `clear_sound_engine_data`）。

### 配色（背景调色板 `con_bg_pal_03` @ `$D595`）

字形 tile 只用 2bpp 的像素值 0 和 3，所以每个子调色板只有「颜色 3」决定文字颜色：

| 元素 | 颜色 |
|---|---|
| `HI-SCORE` 标签、`Ⅰ/Ⅱ-PLAYER`、`BONUS!` | `#F83800` 亮红橙 |
| 最高分数字、1P/2P 总分 | `#FCA044` 琥珀 |
| `STAGE`、统计行、横线、`TOTAL`、`1000 PTS` | `#FCFCFC` 白 |

## 附：换算到 2.5 倍缩放的实现（TankWar 项目）

| 项目 | 原版 | ×2.5 |
|---|---|---|
| 瓦格 | 16px | 40px |
| tile（通行单位） | 8px | 20px |
| 子块（破坏单位） | 4px | 10px |
| 坦克 | 16px | 40px |
| 网格吸附 | 8px | 20px |
| 普通弹一发 | 16×4 | 40×10 |
| 3 星弹一发 | 16×8 | 40×20 |

**坦克宽 = 一整瓦 = 炮弹凿墙带宽**，三者必须恒等，否则会出现「凿出的路自己钻不过去」。
